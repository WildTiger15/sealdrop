# Crypto primer (one page)

This primer is a starting point. Rewrite it in your own words in `docs/CONCEPTS.md`.

**KEM (Key Encapsulation Mechanism).** A KEM is a public key tool with exactly one job: let a sender and a receiver agree on a fresh random secret. The receiver publishes a public key. The sender runs `Encapsulate(public key)` and gets two things back: a *shared secret* to keep, and a *ciphertext* to send. The receiver runs `Decapsulate(ciphertext, private key)` and gets the same shared secret. A KEM never encrypts your file directly. It hands out a key, and a symmetric cipher uses that key to encrypt the file.

**X25519 vs ML-KEM.** X25519 is Diffie-Hellman on an elliptic curve (Curve25519). It is small (32 byte keys), fast, and has been trusted for about 20 years. A large quantum computer running Shor's algorithm would break it. ML-KEM (FIPS 203, formerly Kyber) is built on a lattice problem called Module Learning With Errors, which nobody knows how to solve efficiently, even with a quantum computer. ML-KEM is the NIST post quantum standard, but it is young, and its keys are much bigger (1184 byte public key, 1088 byte ciphertext).

**Why hybrid.** Today we can't be sure about either algorithm alone. X25519 is well studied but quantum-vulnerable. ML-KEM resists quantum attacks but has had less time under attack, and its implementations are newer. A hybrid KEM runs both and mixes the two secrets together, so an attacker has to break *both* to learn the key. This matters for "harvest now, decrypt later" attacks: someone can record your encrypted file today and wait for a quantum computer. X-Wing is a specific, carefully analysed hybrid: SHA3-256 over both secrets, the X25519 ciphertext, the X25519 public key and a label.

**KEM vs signature.** A KEM gives *confidentiality*: only the recipient can read the file. A signature gives *authenticity*: the recipient can prove who sent the file and that nobody changed it. Encryption alone can't do this, because anyone who knows the recipient's public key can encrypt a file to them. SealDrop uses ML-DSA-65 (FIPS 204), the NIST post quantum signature standard.

**AEAD (Authenticated Encryption with Associated Data).** An AEAD encrypts data and also attaches a tag, which is a cryptographic checksum keyed by the secret key. When decrypting, the tag is checked first, and if even one bit has changed, decryption fails and returns nothing. "Associated data" is extra data (like a file header) that isn't encrypted but is covered by the tag. SealDrop uses XChaCha20-Poly1305. Its 24 byte nonce is large enough to pick at random safely.

**HKDF.** HKDF (RFC 5869) turns some secret input material into one or more keys of the size you need. It has two steps: *extract* (concentrate the randomness) and *expand* (produce output keys). An `info` label separates the keys, so "the file key" and "the key-wrapping key" can never come out the same even from the same input.

**Constant time.** Code is constant time when how long it takes doesn't depend on secret values. Here is how a timing leak happens: a normal `==` on two byte strings stops at the first byte that differs. An attacker who can time the comparison then learns how many leading bytes they guessed right, and can recover the secret one byte at a time. Constant time code (for example the `subtle` crate's `ct_eq`) always touches every byte, and avoids branches and memory lookups that depend on secrets.

**Why never write your own primitives.** Cryptography fails silently. A broken cipher still produces output that looks random, and your tests still pass. Real attacks come from details you don't see by testing the output: timing leaks, missing input validation (ML-KEM has a required key check), bad randomness, edge cases in the math. Well known crates such as RustCrypto's are written to published standards, checked against official test vectors, and reviewed by many people. Our job is to *combine* them correctly, by following a published spec (the X-Wing draft) exactly, and to prove it with the spec's own test vectors.
